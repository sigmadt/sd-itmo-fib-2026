# Практика 3. UML и паттерны GoF

Есть сервис уведомлений интернет-магазина: письма, SMS и Telegram. Он работает, но устроен плохо. Сегодня мы сначала нарисуем, как он устроен, а потом переделаем его на паттерны из лекции так, чтобы поведение не поменялось ни на символ.

Работаем вместе в VS Code Live Share.

**Что делает сервис:** техническое задание в `spec.md`. Прочитайте его первым, по нему проще разобраться в коде и нарисовать диаграммы.

| Время | Что |
|---|---|
| 0:00-0:08 | Вход в Live Share, знакомство с кодом |
| 0:08-0:30 | Часть 1. Диаграммы |
| 0:30-1:05 | Часть 2. Рефакторинг на паттерны |
| 1:05-1:20 | Разбор |

## Код

Одна и та же программа на двух языках, берите свой:

| Папка | Запуск | Проверка |
|---|---|---|
| `python/` | `python3 main.py` | `./check.sh` |
| `java/` | `./check.sh` (собирает и запускает) | `./check.sh` |

В каждой папке:
- `main.py` / `Main.java`: сценарий «заказ отправлен, уведомляем покупателя и склад»;
- `notifier.py` / `Notifier.java` и остальное: сам сервис;
- `legacy_sms.py` / `LegacySmsGateway.java`: библиотека SMS-провайдера. **Это чужой код, его менять нельзя;**
- `expected_output.txt`: эталонный вывод. **Его тоже менять нельзя;**
- `check.sh`: запускает сценарий и сравнивает вывод с эталоном.

`check.sh` наша страховка. Рефакторинг меняет устройство кода, но не его поведение. Если после ваших изменений `./check.sh` пишет OK, вы ничего не сломали.

## Часть 1. Диаграммы (22 мин)

Рисуем в Mermaid: это текст, который превращается в картинку. Его удобно править вместе, и GitHub показывает его как диаграмму. Шпаргалка по синтаксису: `diagrams/mermaid.md`.

Чтобы видеть картинку в VS Code, поставьте расширение **Markdown Preview Mermaid Support** (`bierner.markdown-mermaid`) и откройте предпросмотр: `Cmd/Ctrl+Shift+V`.

Скопируйте `diagrams/_template.md` в `diagrams/Фамилия.md` и нарисуйте:

1. **Диаграмму классов кода как есть.** Какие классы, что в них лежит, кто кого использует. Не идеальную, а честную: если `Notifier` знает про все каналы сразу, это должно быть видно.
2. **Диаграмму последовательности** для отправки SMS: от `main` до шлюза, с повтором после ответа 503. Подсказка: посмотрите вывод `./check.sh`, там видно, что происходит по шагам.

Потом сделаем одну общую компонентную диаграмму на всех.

## Часть 2. Рефакторинг (35 мин)

Скопируйте код своего языка в личную папку и работайте только в ней:
```
cp -r python work/Фамилия
```
или
```
cp -r java work/Фамилия
```

Задачи ниже. Каждая это запах в коде и паттерн, который его лечит. Берите по порядку своего трека. После каждой задачи `./check.sh` должен писать OK.

| # | Запах | Паттерн | Готово, когда |
|---|---|---|---|
| 1 | `Message` создается с 10 параметрами подряд: `None, "high", False, None, None, True, None` | Builder | В `main` сообщения собираются по шагам, по имени каждого параметра понятно, что он значит |
| 2 | `Notifier.send` выбирает канал цепочкой `if/elif` | Factory | У каждого канала свой класс с общим методом `send`, канал создается по имени в одном месте |
| 3 | `AppConfig` один на всю программу, и `Notifier` берет его сам, в обход параметров | Singleton → DI | Конфиг передается через конструктор. Его можно подменить в тесте |
| 4 | Ветка SMS сама переводит номер в цифры, текст в cp1251 и разбирает коды ответа шлюза | Adapter | Шлюз обернут в класс с тем же интерфейсом, что у остальных каналов |
| 5 | Повторы и логирование скопированы в каждый канал | Decorator | Повторы с логом это обертка, которая работает с любым каналом. В каналах их нет |
| 6 | Группы получателей это словари, и код проверяет `isinstance` | Composite | Получатель и группа отвечают на один и тот же вызов, рекурсия без проверок типов |
| 7 | `main` сам собирает конфиг, сервис, сообщения и группы | Facade | Клиентский код говорит с одним объектом |
| ★ | Похожие сообщения собираются заново каждый раз | Prototype | Есть шаблон сообщения, от которого делают копии и меняют получателя |

**Треки:**
- **начинаю:** 1 → 2;
- **уверенно:** 2 → 4 → 5, потом 1;
- **опытный:** все по порядку, потом ★. Для каждого паттерна ответьте в своем файле в `diagrams/`: где он здесь окупился, а где был бы лишним.

Задачи 4 и 5 удобнее делать после 2: им нужен общий интерфейс канала.

**Когда закончили задачу**, допишите в свой файл в `diagrams/` диаграмму классов **после** рефакторинга. Только ту часть, которую вы меняли.

## Правила

- Каждый работает в своей папке `work/Фамилия/` и в своем файле `diagrams/Фамилия.md`. В чужие не пишем.
- Сохраняйте файлы (`Cmd/Ctrl+S`), иначе они могут не дойти до преподавателя.
- `legacy_sms` и `expected_output.txt` не меняем. `main` менять можно, но вывод должен остаться прежним.
